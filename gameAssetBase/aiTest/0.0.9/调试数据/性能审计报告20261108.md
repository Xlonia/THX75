TH75 性能审计（2026-11-08 现役）：成本分档归因与 800@60 可行性
---

## 一、结论

**1. 800 弹幕 60fps：架构上可行，稳态实测已达标，但当前处于"贴线状态"——总工作量恰好压在 16.7ms 门槛上，任何一段尖峰都会因 vsync 量化直接翻倍成 33ms（30fps）。** 判定：**"已部分达成 + 需改造才能稳定"**，不是架构性不可行。
**2. 用户对"热力图/AI 是主因"的质疑：数据上"先成立、后不成立"——这是被具体实现方式而非功能本身决定的。**

- **成立的部分（11-07 19:26 那次重载运行）**：函数级归因显示 `_sit_tick` 5.40ms/帧 + RetSystem（compute_sp 4.95 + avatar_ok 4.88）+ HeatmapField.sample_read 2.57 ≈ **17.8ms/帧，占该运行平均帧 42%**【已查证，来自 11071926.csv 逐帧 Profiler】。也就是说：在那版实现下，**热力图/AI 相关确实是最大单项**，但成因是"没摊平"（RET 树搜索单帧 21-24ms spike、态势 tick 未轮转、回读未合并），不是功能必要成本。
- **不成立的部分（11-08 01:10 最新运行）**：同一套功能经修复后，script 仅 **3.03ms/帧（占 17%）**，p99 = **16.8ms（满 60fps）**【已查证，11080110.csv】。异常帧与 `frame%6==0` 无关联（56 组残差平均帧时间平坦，异常帧落在 %6 残差的比例 16.0%/15.0%/3.1%/11.8%，不高于基线 16.7%）——**"每 6 帧 tick 集中爆发"作为当前主因已被否证**【已查证】。
- **当前真正的主因**（团队分块计时 `_dbg_split` + live 分档实测）：**proc 侧等高面绘制与 display 回读 5.5-6.5ms** + **弹幕更新 6-7ms（随弹量）** + 态势 3.5ms + AI 1.5ms；650-750 弹时合计 15.5-18.5ms，越过 16.7ms 门槛即被 vsync 翻倍到 33ms。另有一个 **11-08 最新观察项：live 探针 proc 段升至 21-24ms（此前 5-7ms），待复跑对账**【待复跑】。
  **3. 为什么"800 左右开始低于 60"（作者标准）：不是因为热力图/AI，而是预算结构贴线。** 物理 ~5-7ms + proc ~5.5-6.5ms + 态势/AI ~5ms ≈ 15.5-18.5ms，与 16.7ms 门槛同量级；弹量一到 700-800 就越线，vsync 两跳变成 33ms。要稳定 800@60，必须把总工作量压到 ~13ms 以下留余量——改造方向见第五节。

## 四、800 弹幕 60fps 论证

**基准（可引用数据）**

- 09-30 bench：100 弹 phys 均 2.16ms/峰 7.96；500→7.43/28.17；1000→**9.79/23.02**（贴 10ms 线）；2000→**23.25/42.99**（超线 2.3×）。斜率≈12.5µs/弹、截距≈1.2ms（TECH_SPEC 同口径）【已查证】
- 现役团队自测（battle_tick_perf，真实默认队）：**5.00ms/436 弹 → 6.90ms/962 弹**（0.0.8 末基线 → 11-07 多轮回归 5.82-7.41ms/678-1013 弹），即 **≈6-7µs/弹**【已查证，工作清单逐轮记录】
- live_smoke 真渲染 60s（11-07 修复后）：p50 16.7 / p90 28.4 / p99 73.4 / max 106.8ms【已查证】
  **现役每弹每帧操作清单**（A1-A8）：快路径（frozen/预采样表）≈**1.5-3µs/弹**；表达式兜底≈**6-8µs/弹**；混合估算≈**4µs/弹**（0.7×2.5+0.2×7+0.1×8）【推断，最大不确定项：现役 frozen/表/闭包/兜底占比未实测，需 `_dbg_split`+`_dbg_acc` 复跑统计】。
  **算式链**：
- 800×4µs=3.2ms + 固定 3.5ms（hash 维护/火控/命中 30Hz/杂项）= **6.7ms physics**
- +渲染侧 draw_bullet_mm ≈2ms（render 线程）
- +proc 侧（等高面+回读）5.5-6.5ms
- +态势/AI 摊平 ≈5ms（态势 3.5 + AI 1.5）
- 合计 ≈15.5-18.5ms vs 16.7ms 门槛 → **贴线**，越过即 vsync 翻倍 33ms
  **瓶颈层判定：三者叠加，按权重排序**
1. **proc 侧等高面光栅化（最大单项，5.5-6.5ms）**：分层设色多边形每帧全量重绘 + display 回读；三刀（绘制降 10Hz、每层 cap 36、提取 cap 1200/段）后铺场爆发段 173→30-50ms，仍未达 60fps【已查证】
2. **GDScript 单弹成本天花板（6-7µs/弹×800≈5ms）**：语言层；C++ 批量运动学/哈希/ctx 已编译但**未接线**（`_bulk_skip` 仅置 false、project.godot 无 `[gdextension]`、release.dll 缺失）——当前运行不含任何 C++ 加速【已查证】
3. **调度模式与历史实现缺陷（已修但留观察项）**：catch-up 雪崩（已渲染帧驱动解决）、永生弹 800+（已兜底）、O(n²) 回收（已 swap-remove）、热力幻影（已修）——均已修复；**但 11-08 第三十轮观察项：live 探针 proc 段 21-24ms（此前 5-7ms），疑似回归，待 F5 对账**【待复跑】
   **结论表述（回答用户问题）**：

> 800 弹 60fps 在现役架构下**不是做不到，而是"稳态勉强达标、增幅即掉档"**：11-07 live 实测 720-813 弹稳态 16.6-17ms 满 60fps 达标；不达标的是①铺场爆发段（316→845 攀升期，三刀后仍 30-50ms）②800-1200 弹带（35-41ms≈30fps，比标准差 2 倍）③11-08 最新 proc 观察项待对账。**原因不是热力图/AI 计算本身（摊平 9%），而是 proc 侧等高面光栅化 + 每弹 6-7µs 的 GDScript 成本 × 800 + 总预算贴线后的 vsync 量化**。达到稳定 800@60 需要把总工作量从 ~16-18ms 压到 ≤13ms，最小改造集见下。
